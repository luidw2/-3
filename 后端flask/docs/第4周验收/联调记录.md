## 2. 配置核对结果

### 2.1 证书

- 仓库最初只提交了 `app/certs/server/server.crt`（CN=localhost，SAN 含 DNS:localhost、IP:127.0.0.1），**对应的 `server.key` 与签发它的 CA 私钥均未入库**，原 HTTPS 链路无法在本机恢复。
- 处理：按标准 PKI 结构重新生成本地两级证书（私钥均不入库）：
  - `app/certs/server/ca_local.crt`：本地 CA（CN=Local Dev Secure ECommerce CA，`basicConstraints CA:TRUE`，10 年有效）；
  - `app/certs/server/server.crt`：服务器证书，由本地 CA 签发，CN=localhost，SAN=DNS:localhost、IP:127.0.0.1，`extendedKeyUsage=serverAuth`，1 年有效；
  - `app/certs/server/server.key`：服务器私钥。
- 信任方式：把 `ca_local.crt` 导入当前用户“受信任的根证书颁发机构”后，浏览器访问不再告警（Chrome 要求根证书具备 CA 属性，这是第一次直接用自签证书仍被拦截的原因）。

### 2.2 跨域（CORS）

- 前端 `http://127.0.0.1:5173` 与后端 `https://127.0.0.1:5000` 端口/协议不同，属于跨域请求。
- `config/config.py` 的 `CORS_ORIGINS` 白名单已包含 `http://localhost:5173`、`http://127.0.0.1:5173`；`_configure_cors` 放行 `Content-Type`、`Authorization` 头并允许 OPTIONS 预检。
- 实测：浏览器登录时 OPTIONS 预检 200 通过，POST 成功，无 CORS 报错。

### 2.3 环境变量

- 后端此前没有 `.env`，隧道 SM2 密钥与数据库口令均缺失。已创建：
  - `后端flask/.env`：真实配置（含本机口令/私钥），并在 `后端flask/.gitignore` 中增加 `.env`，不入库；
  - `后端flask/.env.example`：可入库的模板，新机器复制后按本机情况填写。
- 前端本机创建 `v1-zhognshe-rebuild-3-vue/.env`：`VITE_API_BASE_URL=https://127.0.0.1:5000`、`VITE_SM2_FLASK_PUBLIC_KEY`、`VITE_SM2_VUE_PRIVATE_KEY`（与后端同一套密钥）。
- 仓库根 `.gitignore` 规定所有 `.env` 不入库（PUBLIC 仓库），因此前端 `.env` 仅作本机覆盖；同时已把 [src/utils/sm-tunnel.js](../../../v1-zhognshe-rebuild-3-vue/src/utils/sm-tunnel.js) 的内置默认密钥和 [src/request.js](../../../v1-zhognshe-rebuild-3-vue/src/request.js) 的默认地址（HTTPS）同步更新为新值，其他机器即使没有前端 `.env` 也能直接与后端 demo 配置联调。
- 顺带修复一个实际问题：MySQL 重置后的口令含 `@`，`app/utils/db.py` 直接字符串拼接 URL 时口令被当作分隔符（主机名被解析成 `123456@127.0.01`），已在 [app/utils/db.py](../../app/utils/db.py) 中对口令做 `urllib.parse.quote_plus` 编码。

## 3. 真实登录联调

联调步骤：

1. 在 `后端flask` 目录启动后端：`.venv\Scripts\python.exe run.py`（HTTPS）。
2. 在 `v1-zhognshe-rebuild-3-vue` 目录启动前端：`npm run dev`。
3. 浏览器打开 `http://127.0.0.1:5173/user/login`，输入用户名 `zhangsan`、密码 `123456`，角色保持“用户”，点击“登录”。

结果：

- 浏览器发出的请求为 `POST https://127.0.0.1:5000/user/login`，原始请求体为隧道包 `{"env":"<base64>","data":"<base64>"}`，其中**不含用户名 `zhangsan`、密码 `123456` 的任何明文**；
- 后端解密后完成 Bcrypt 比对并签发 JWT，原始响应体同样为 `{"env":...,"data":...}` 隧道包；
- 页面提示“登录成功”并跳转首页 `http://127.0.0.1:5173/`（见 [登录成功-首页.png](登录成功-首页.png)）；
- `localStorage` 中写入 268 字符的 access_token；登录后 `GET /user/profile` 携带该 JWT 调用成功（HTTP 200），令牌链路正常。

补充：曾出现页面长时间停留后登录返回 401 的情况，硬刷新页面（重新加载最新模块）后恢复，属于浏览器旧会话问题，非接口缺陷。

## 4. 会话密钥 / IV / Nonce 随机性检查

- 后端侧：连续封包 **50 次**，用后端私钥逐个拆信封取出 `key/iv/nonce`：
  - 三者均为 32 字符 hex（16 字节随机），长度分布全部正确；
  - key、iv、nonce 的唯一个数均为 **50/50**；
  - 拼接后十六进制字符频率 max/min 偏差小于 1.3 倍，分布均匀。
- 前端侧（浏览器控制台）：连续调用 `sealRequest` **20 次**，`env` 与 `data` 字段唯一个数均为 **20/20**（`data` 唯一即说明每次会话密钥/IV 不同）。

结论：每次会话的会话密钥、IV 与 Nonce 全部不同，满足验收要求。
