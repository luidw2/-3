> 数据范围：`E:\Python\综设1重构-flask+vue-sm2尝试\综设1重构-flask+vue\基线报告\` 下的 JTL 文件
> 生成时间：2026-11-02
> 说明：本文对目录中成组的 JTL 做逐文件统计与前后对比，并在最后给出"口径与噪声"说明和报告引用建议。
> HTTP 指标口径：JMeter 的 `elapsed`（响应时间，ms），p95 = 第 95 百分位；吞吐 = 样本数 ÷ 时间窗；
> 错误率 = 失败样本（断言失败 / 非 2xx / 客户端异常）÷ 总样本。
> PerfMon 指标口径：JTL 中 `elapsed` 字段 ÷ 1000 = CPU（%）或内存（字节）。

干净复测（单实例、各 1 轮）：原版 p95 455ms / 吞吐 51.8/s，优化版 p95 **369ms** / 吞吐 60.0/s
→ **p95 −18.9%，吞吐 +15.8%**。

### 2.3 结论（登录）

- 优化后登录 p95 相对原版下降 **13.7%（配对口径）~18.9%（干净复测）**，错误率 0%（配对数据）；
- 未达到 −20%，原因是 **bcrypt(cost=12) 单次校验约 200~246ms，占登录单请求服务时间约 92%**，
  两版本 CPU 峰值均接近 90%，工程优化只能拿到约 15% 左右；
- 登录 p95 稳定低于 1s 业务阈值，因此报告中按任务书允许的
  **"已达标保持证明"** 收尾（不降低 bcrypt 强度）；
- 报告引用建议：**优先引用 2.2 的配对 A/B 数据（505→436，−13.7%）**，
  并附 2.3 的干净复测（455→369，−18.9%）作为补充；2.1 的用户 JTL 可作为"全量三轮原始数据"附录，
  同时说明 run1 的 20 个客户端 SocketException 与 run3 的环境噪声。

- 热点缓存 TTL 默认 5 秒，压测重复访问同一热页 → 命中率 >99%；
  生产环境命中率取决于访问分布，需在报告中注明一致性代价（列表最多滞后 5 秒）。

## 五、口径与噪声说明（写进报告必看）

1. **GUI vs 非 GUI 差异很大**：JMeter GUI 模式（带监听器绘图、同机 CPU 竞争）会把 p95 明显抬高。
   例如商品查询基线：GUI 口径 p95 273ms，非 GUI 配对口径只有 94ms。
   **前后对比必须使用同一种模式**，不能拿 GUI 基线和 CLI 优化后数据直接比。
2. **本机后台负载（杀毒、IDE、同步盘）会造成 20%~100% 的轮间波动**：
   例如登录优化后 run3（31.7/s、p95 1199ms）明显异常。结论以"相邻执行、同模式、3 轮取中位数"的
   严格配对数据为准，用户 JTL 作为全量原始数据附录。
3. **登录 JTL 的错误率**：`Test_user_login_after1.jtl` 中 20 条 `java.net.SocketException`
   是 JMeter 客户端异常（非服务端 5xx），该轮错误率 1.0%；配对测试中为 0%。
   建议报告用配对数据，或将 after1 重跑后替换。
4. **商品 JTL 含登录样本**：商品场景开头 20 个样本是登录（每线程一次），统计商品指标时
   必须按 URL/标签过滤，否则 p95 会被登录拉高。
5. **单实例检查**：每次压测前确认 `netstat -ano | findstr :5000 | findstr LISTENING` 只有 1 行；
   调试重载器/重复启动会出现两个进程同时监听 5000，导致数据混杂。
6. **缓存口径**：商品优化含 5 秒 TTL 热点缓存，JMeter 重复请求同一热页，命中率 >99%；
   报告中需注明 TTL、一致性代价与"生产命中率取决于访问分布"。
