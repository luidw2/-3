# 商品查询接口性能优化说明（第 8–9 周）

> 项目：安全电子商务系统（Flask + Vue + SM2 隧道）
> 被测接口：`GET /user/products/profile`（用户浏览商品列表，分页 + 条件过滤）
> 优化日期：2026-10-29
> 关联数据：`基线报告/商品查询接口优化对比/`（配对 A/B 的原始 JTL、JMeter 计划、中间实验数据）
> 对比基线：本次优化**开始前**同一份代码（登录优化版 + 原始商品/JWT 代码）在同一安静时段相邻采集

---

## 1. 背景与瓶颈定位

### 1.1 请求链路（优化前）

```
GET /user/products/profile
 ├─ @jwt_auth_required
 │    └─ verify_access_token(JWT)          # 纯计算，约 0.1ms
 │    └─ db.get_user_by_id(user_id)        # 1 次 SELECT（仅确认账号存在/未禁用）
 ├─ @user_required                         # 纯计算（角色判断）
 └─ 视图 get_all_products()
      └─ db.get_all_products_paginated()
           ├─ count(*) 查询                # 1 次 SELECT
           └─ 分页查询（joinedload 卖家）   # 1 次 SELECT
```

### 1.2 实测瓶颈

| 观察 | 数据 | 结论 |
|---|---|---|
| 每个请求的数据库 SELECT 次数 | MySQL `Com_select` 增量 ÷ 请求数 = **2.98 次/请求** | 每个请求固定 3 次查询 |
| 服务端耗时分布 | 前几个请求 8~27ms，稳定压测时服务端 p50 抬升到 100ms+ | 单进程 GIL 下，每请求的 Python/ORM 工作排队 |
| CPU 占用 | 约 34%（远低于登录的 90%） | **不是 CPU 计算瓶颈**，而是"每请求的数据库往返 + Python/ORM 开销" |
| 数据库规模 | `product` 表仅 3 行，EXPLAIN 全表扫描只扫 2 行 | **SQL/索引不是当前瓶颈**（加索引对本数据量无收益，需在报告中说明） |

因此本接口的优化方向是：**减少每请求的数据库往返与 Python/GIL 开销**，并缓存热点读。

---

## 2. 优化内容（4 项）

| # | 优化项 | 变更文件 | 作用 |
|---|---|---|---|
| 1 | JWT 鉴权用户状态缓存（TTL 5s） | `app/middleware/jwt_auth.py` | 命中时省掉每请求 1 次用户表 SELECT |
| 2 | 热点商品列表缓存（TTL 5s） | `app/utils/hot_cache.py`（新增）、`app/api/v1/product_profile.py` | 命中时直接返回已序列化结果，跳过整条 DB 查询 + ORM 序列化 |
| 3 | 连接池调优 | `app/utils/db.py` | `pool_size` 10→20（≥20 并发线程）；关闭每次取连接前的 `SELECT 1` 探测 |
| 4 | 分页 COUNT 查询优化 | `app/utils/db.py` | COUNT 改为独立的 `COUNT(id)` 查询，避免对带 joinedload 的 ORM 查询做子查询计数；COUNT 与分页查询复用过滤条件 |

> 说明：`product` 表当前仅 3 行，索引优化对当前数据量无显著收益（EXPLAIN 已证明），
> 因此本次没有为"索引"制造虚假收益；索引的验证方法见第 7 节。

## 3. 代码修改前后对照

### 3.1 `jwt_auth.py`：鉴权用户状态缓存

**修改前：**
```python
        # 依据令牌里声明的角色回查对应数据表：
        # seller 查卖家表；admin / auditor 查后台 staff 表；其余(user)查用户表。
        # 以数据库最新状态为准（封禁/注销立即生效的关键）
        if role == 'seller':
            user_or_seller = db.get_seller_by_id(user_id)
        elif role in ('admin','auditor'):
            user_or_seller = db.get_staff_by_id(user_id)
        else:
            user_or_seller = db.get_user_by_id(user_id)
```

**修改后（新增缓存辅助函数 + 调用）：**
```python
import os
import threading
import time
...
_AUTH_USER_CACHE = {}
_AUTH_USER_CACHE_LOCK = threading.Lock()
_AUTH_USER_CACHE_TTL = float(os.getenv('JWT_USER_CACHE_TTL', '5'))
_AUTH_USER_CACHE_MAX = 4096


def _fetch_user_by_role(role, user_id):
    """按令牌里的角色回查对应数据表（与优化前逻辑一致）"""
    if role == 'seller':
        return db.get_seller_by_id(user_id)
    if role in ('admin', 'auditor'):
        return db.get_staff_by_id(user_id)
    return db.get_user_by_id(user_id)


def _fetch_user_by_role_cached(role, user_id):
    """带 TTL 缓存的用户状态查询"""
    now = time.time()
    key = (role, user_id)
    with _AUTH_USER_CACHE_LOCK:
        ent = _AUTH_USER_CACHE.get(key)
        if ent is not None and ent[0] > now:
            return ent[1]
    user = _fetch_user_by_role(role, user_id)
    if user is not None:
        with _AUTH_USER_CACHE_LOCK:
            if len(_AUTH_USER_CACHE) >= _AUTH_USER_CACHE_MAX:
                _AUTH_USER_CACHE.clear()
            _AUTH_USER_CACHE[key] = (now + _AUTH_USER_CACHE_TTL, user)
    return user
...
        # 性能优化：命中缓存时省掉一次数据库往返；
        # 代价：封禁/注销最多延迟 TTL 秒生效（默认 5s）
        user_or_seller = _fetch_user_by_role_cached(role, user_id)
```

### 3.2 `hot_cache.py`（新增）：进程内 TTL 缓存

```python
class TTLCache:
    """极简线程安全 TTL 缓存（dict + 过期时间戳 + 互斥锁）"""
    def __init__(self, ttl=5.0, maxsize=512): ...
    def get(self, key): ...   # 命中返回缓存值，未命中/过期返回 None
    def set(self, key, value): ...
    def clear(self): ...

PRODUCT_LIST_CACHE = TTLCache(
    ttl=float(os.getenv('PRODUCT_CACHE_TTL', '5')),
    maxsize=512,
)
```

| run2 | 基线（原代码） | 86 | 169 | 247 | 92.3 | 0% |
| run3 | 基线（原代码） | 55 | 84 | 111 | 113.8 | 0% |

### 5.2 收益归因（中间实验：只关掉热点缓存）

| 配置 | p50 | p95 | 吞吐 | 相对基线 |
|---|---|---|---|---|
| 基线（原代码） | 69 | 94 | 103.5/s | — |
| 仅 JWT 缓存 + 连接池 + COUNT 优化（`PRODUCT_CACHE_TTL=0` 关闭热点缓存） | 36 | 56 | 125.9/s | p95 −40.4% |
| 再加热点商品缓存（完整优化版） | 15 | 28 | 147.3/s | **p95 −70.2%** |

### 5.3 数据库调用次数（MySQL `Com_select` 增量）

| 版本 | 3 轮总请求 | Com_select 增量 | 每请求 SELECT |
|---|---|---|---|
| 基线（原代码） | 6060 | 18,060 | **2.98 次/请求** |
| 优化版 | 6060 | 151 | **0.025 次/请求（≈ −99.2%）** |

说明：热点缓存 TTL 5 秒，JMeter 反复请求同一热页，缓存命中率 > 99%；
生产环境命中率取决于访问分布（热门商品/首页高、冷门筛选低）。

## 7. 关于"数据库索引"的说明（诚实记录）

`product` 表当前仅 3 行，`EXPLAIN` 显示全表扫描只扫描 2 行，索引对本数据量**无可测量收益**。
为验证索引价值，建议在报告中补一个**临时表实验**（不影响业务数据）：

```sql
CREATE TABLE product_bench LIKE product;
INSERT INTO product_bench ... -- 灌入 10000 行
EXPLAIN SELECT * FROM product_bench WHERE status='active' ORDER BY created_at DESC LIMIT 20;
-- 分别测"无索引 / 加 (status, created_at) 索引"的扫描行数与耗时
DROP TABLE product_bench;
```

结论应写成："当前数据量下索引不是瓶颈；数据量增长到万级后，
`(status, created_at)` 索引可将全表扫描变为范围扫描，是必要优化。"

## 8. 局限与风险

1. **一致性**：热点商品列表最多滞后 TTL（默认 5 秒），商品列表非强一致数据，可接受；
2. **部署形态**：缓存是进程内的，若改为多进程部署，每进程一份、命中率按进程数下降，
   可升级为 Redis 共享缓存（`redis` 客户端已在依赖中）；
3. **压测数据分布**：JMeter 固定请求同一热页，命中率接近 100%；
   报告需注明"生产命中率取决于实际访问分布"，并给出 TTL 与一致性说明；
4. **鉴权缓存**：封禁/改角色最多延迟 5 秒生效（`JWT_USER_CACHE_TTL` 可调）；
5. **后台负载**：本机后台程序（杀毒/IDE/同步）会造成 20%~100% 的轮间波动，
   所有结论均基于相邻执行的配对测量。

## 10. 结论

- 用户浏览商品接口 p95 **94 → 28 ms（−70.2%）**，吞吐 **+42.4%**，错误率 **0%**，
  超过任务书"p95 下降不少于 20%"的要求；
- 收益来源（归因）：JWT 鉴权缓存 + 连接池/COUNT 优化贡献约 **−40% p95**，
  热点商品缓存再贡献到 **−70%**；每请求数据库 SELECT 从 **2.98 次降到 0.025 次**；
- 代价与局限已在第 8 节列明（TTL 一致性、单进程序内缓存、命中率依赖访问分布）。
