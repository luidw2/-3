## 二、优化 1：日志降噪

### 2.1 问题

原实现中，每个请求会写 2~3 条 INFO 日志：

- `app` 日志器的 `REQ ... (xxms)`（控制台 + `backend.log`）；
- werkzeug 自带的逐请求访问日志（`backend.log`）。

在 20 并发下，logging 的内部锁会让这些同步写操作互相排队。

### 2.2 修改前代码（`app/utils/logging_config.py`）

```python
def _console_handler() -> logging.Handler:
    handler = logging.StreamHandler()
    handler.setFormatter(logging.Formatter('%(levelname)s %(message)s'))
    return handler
...
    # werkzeug 访问日志：保留其默认控制台输出，同时追加到文件
    wz = logging.getLogger('werkzeug')
    if file_h not in wz.handlers:
        wz.addHandler(file_h)
    wz.setLevel(logging.INFO)
```

### 2.3 修改后代码

```python
# 性能优化开关（第8-9周）：控制台默认只输出 WARNING；werkzeug 逐请求日志默认关闭。
# 恢复开发期输出：LOG_CONSOLE_LEVEL=INFO、LOG_WERKZEUG_LEVEL=INFO
_CONSOLE_LEVEL = os.getenv('LOG_CONSOLE_LEVEL', 'WARNING').upper()
_WERKZEUG_LEVEL = os.getenv('LOG_WERKZEUG_LEVEL', 'WARNING').upper()

def _console_handler() -> logging.Handler:
    handler = logging.StreamHandler()
    handler.setFormatter(logging.Formatter('%(levelname)s %(message)s'))
    handler.setLevel(getattr(logging, _CONSOLE_LEVEL, logging.WARNING))
    return handler
...
    # werkzeug 访问日志：默认降为 WARNING（不再每条请求写一行）
    wz = logging.getLogger('werkzeug')
    if file_h not in wz.handlers:
        wz.addHandler(file_h)
    wz.setLevel(getattr(logging, _WERKZEUG_LEVEL, logging.WARNING))
```

### 2.4 说明

- `backend.log` 里的 `REQ POST /user/login -> 200 (xxms)` **仍然保留**（服务端耗时证据不丢）；
- 只是不再逐条刷控制台、不再重复记录 werkzeug 访问日志；
- 需要开发期详细日志时用环境变量恢复，无需改代码。

## 三、优化 2：登录链路数据库写合并（条件短事务）

### 3.1 问题

优化前，一次成功登录 = **4 次数据库会话 + 3 次独立提交**：

| 顺序 | 代码调用 | 数据库操作 | 行锁 | commit |
|---|---|---|---|---|
| 0 | `db.get_user_by_username`（视图前段） | SELECT | 无 | — |
| 1 | `db.reset_failed_login(user_)` | SELECT … FOR UPDATE + UPDATE | **有** | 1 |
| 2 | `auth.generate_refresh_token(user_)` → `db.create_refresh_token` | INSERT | 无 | 1 |
| 3 | `db.log_security_event(...)` | INSERT | 无 | 1 |

问题：commit 次数多（MySQL `innodb_flush_log_at_trx_commit=1`，每次提交都刷盘）；
失败计数已是 0 时仍然 `SELECT … FOR UPDATE` + UPDATE，白加行锁。

### 3.2 修改前代码（`app/api/v1/login.py` 成功分支）

```python
    if my_bcrypt.compare_password(user_.password, password):
        # 登录成功：清零历史失败次数（解除失败记录与锁定标记）
        db.reset_failed_login(user_)
        access = auth.generate_access_token(user_, None)
        refresh = auth.generate_refresh_token(user_)
        db.log_security_event('USER_LOGIN_OK', user_.username,
                              f'前台账号登录成功 (role={actual_role}, id={user_id})')
        return build_response(code=0, message='登录成功', data={...})
```

### 3.3 修改后代码

**① 新增 `auth.generate_refresh_token_value()`（只生成、不落库）**

```python
def generate_refresh_token_value(user_or_seller):
    now = _now_utc()
    exp = now + timedelta(days=REFRESH_TOKEN_TTL_DAYS)
    token = secrets.token_urlsafe(48)
    return token, exp.replace(tzinfo=None)
```

（原 `generate_refresh_token()` 保留不动，证书登录 `cert_login.py` 仍在使用。）

**② 新增 `db.complete_login_success()`（条件短事务 + 无锁写令牌/审计）**

```python
def complete_login_success(user, refresh_token, expires_at, event_details, need_reset=False):
    is_seller = getattr(user, 'role', '') == 'seller'
    model = Seller if is_seller else User
    # 第一步（仅必要时）：短事务重置失败计数，行锁持有时间最短
    if need_reset:
        with Session() as session:
            db_user = session.query(model).filter_by(id=user.id).with_for_update().one()
            db_user.failed_attempts = 0
            db_user.lock_until = None
            session.commit()
    # 第二步：写 refresh_token + 审计（无行锁，单事务提交）
    with Session() as session:
        session.add(RefreshToken(
            user_id=None if is_seller else user.id,
            seller_id=user.id if is_seller else None,
            token=refresh_token, expires_at=expires_at))
        session.add(SecurityEvent(event_type='USER_LOGIN_OK',
                                  username=user.username, details=event_details))
        session.commit()
```

**③ `login.py` 成功分支改为：**

```python
    if my_bcrypt.compare_password(user_.password, password):
        access = auth.generate_access_token(user_, None)
        refresh, refresh_exp = auth.generate_refresh_token_value(user_)
        need_reset = bool(getattr(user_, 'failed_attempts', 0) or getattr(user_, 'lock_until', None))
        db.complete_login_success(user_, refresh, refresh_exp,
                                  f'前台账号登录成功 (role={actual_role}, id={user_id})',
                                  need_reset=need_reset)
        return build_response(code=0, message='登录成功', data={...})
```

### 3.4 关键细节：第一版失败尝试（已修正）

第一版把"行锁重置 + 两条 INSERT"放在同一个长事务里：

```python
with Session() as session:
    db_user = session.query(User).filter_by(id=user.id).with_for_update().one()  # 持锁
    ...
    session.add(RefreshToken(...))     # 持锁期间 INSERT
    session.add(SecurityEvent(...))    # 持锁期间 INSERT
    session.commit()                   # 锁持有到提交
```

压测（20 个 VU 全部用同一账号 `user_1`）时，20 个请求争抢**同一 user 行锁**：
行锁持有时间从约 2.5ms 拉长到约 6.5ms，p95 反而升到 **1281ms**、吞吐掉到 32.5/s
（此数据文件已作废，仅作过程记录）。

修正方案：**正常登录不碰 user 行锁**——只有 `failed_attempts`/`lock_until` 非空时才进入
短事务重置；写 refresh_token 与审计放在无行锁的独立事务里。修正后恢复并优于基线。

### 3.5 实测效果

| 指标 | 基线（原代码） | 优化后 | 变化 |
|---|---|---|---|
| 数据库会话数（成功登录） | 4 | **2**（正常路径） | −50% |
| commit 次数（成功登录） | 3 | **1**（正常路径） | −67% |
| 单请求写库耗时（组件计时） | 12.0 ms | **6.5 ms** | −46% |
| 三轮 A/B p95（CLI 配对） | 505 ms | **436 ms** | **−13.7%** |
| 干净复测 p95 | 455 ms | **369 ms** | **−18.9%** |
| 错误率 | 0% | 0% | 不变 |

> 登录 p95 受 bcrypt(cost=12) 限制（单次约 200–246ms，占单请求约 92%），
> 因此工程优化只能拿到约 14%~19%；登录以"已达标保持证明（p95 < 1s）"收尾。
> 详细数据见 `基线报告/登录接口优化对比/登录接口优化说明.md`。

## 四、优化 3：JWT 鉴权用户状态缓存

### 4.1 问题

`jwt_auth_required` 对每个受保护请求都回查一次数据库（`get_user_by_id` / `get_seller_by_id` /
`get_staff_by_id`），只为确认"账号仍存在且未被禁用"。商品查询压测中，MySQL `Com_select`
增量 ÷ 请求数 ≈ **2.98 次/请求**，其中 1 次就是这里的回查。

### 4.2 修改前代码（`app/middleware/jwt_auth.py`）

```python
        # 依据令牌里声明的角色回查对应数据表
        if role == 'seller':
            user_or_seller = db.get_seller_by_id(user_id)
        elif role in ('admin','auditor'):
            user_or_seller = db.get_staff_by_id(user_id)
        else:
            user_or_seller = db.get_user_by_id(user_id)
```

### 4.3 修改后代码

```python
import os, threading, time

_AUTH_USER_CACHE = {}
_AUTH_USER_CACHE_LOCK = threading.Lock()
_AUTH_USER_CACHE_TTL = float(os.getenv('JWT_USER_CACHE_TTL', '5'))
_AUTH_USER_CACHE_MAX = 4096

def _fetch_user_by_role(role, user_id):
    if role == 'seller':
        return db.get_seller_by_id(user_id)
    if role in ('admin', 'auditor'):
        return db.get_staff_by_id(user_id)
    return db.get_user_by_id(user_id)

def _fetch_user_by_role_cached(role, user_id):
    now = time.time(); key = (role, user_id)
    with _AUTH_USER_CACHE_LOCK:
        ent = _AUTH_USER_CACHE.get(key)
        if ent is not None and ent[0] > now:
            return ent[1]
    user = _fetch_user_by_role(role, user_id)
    if user is not None:
        with _AUTH_USER_CACHE_LOCK:
            if len(_AUTH_USER_CACHE) >= _AUTH_USER_CACHE_MAX:
                _AUTH_USER_CACHE.clear()
            _AUTH_USER_CACHE[key] = (now + _AUTH_USER_CACHE_TTL, user)
    return user

# 调用处：
user_or_seller = _fetch_user_by_role_cached(role, user_id)
```

### 4.4 说明与代价

- 缓存键 `(role, user_id)`，只缓存"确认存在"的用户，不缓存 None；
- **代价**：封禁/改角色最多延迟 TTL 秒（默认 5s）生效，TTL 可由 `JWT_USER_CACHE_TTL` 调整；
- 与原始逻辑完全一致：缺 token / Bearer 格式错 / 验签失败 / 用户被禁用 仍返回 401。

## 五、优化 4：商品列表热点缓存

### 5.1 问题

商品浏览页是典型"热点读"：大量用户反复访问相同的分页 URL。
原实现每次请求都要：JWT 回查（1 次 SELECT）→ 分页 COUNT（1 次）→ 分页查询（1 次）
→ 逐条 ORM 对象转字典 → JSON 序列化。20 并发下单进程 GIL 下产生排队。

### 5.2 修改前代码（`app/api/v1/product_profile.py`）

```python
        result = db.get_all_products_paginated(page=page, per_page=per_page,
                                               status=status, seller_id=seller_id,
                                               name_keyword=keyword)
        items_data = []
        for product in result['items']:
            items_data.append({...逐字段序列化...})
        return build_response(code=0, message='查询成功', data={
            'items': items_data, 'total': result['total'],
            'page': result['page'], 'size': result['per_page'],
            'pages': result['pages']})
```

### 5.3 修改后代码

**新增 `app/utils/hot_cache.py`（进程内线程安全 TTL 缓存）**

```python
class TTLCache:
    def __init__(self, ttl=5.0, maxsize=512): ...
    def get(self, key): ...      # 命中返回缓存值；未命中/过期返回 None
    def set(self, key, value): ...
    def clear(self): ...

PRODUCT_LIST_CACHE = TTLCache(
    ttl=float(os.getenv('PRODUCT_CACHE_TTL', '5')),
    maxsize=512,
)
```

**`product_profile.py` 视图改为：**

```python
        cache_key = (page, per_page, status, seller_id, keyword)
        payload = PRODUCT_LIST_CACHE.get(cache_key)

        if payload is None:
            result = db.get_all_products_paginated(...)
            items_data = [...逐条序列化...]
            payload = {'items': items_data, 'total': result['total'],
                       'page': result['page'], 'size': result['per_page'],
                       'pages': result['pages']}
            PRODUCT_LIST_CACHE.set(cache_key, payload)

        return build_response(code=0, message='查询成功', data=payload)
```

### 5.4 说明与代价

- 缓存键包含全部分页/过滤参数 `(page, per_page, status, seller_id, keyword)`；
- TTL 默认 5 秒（`PRODUCT_CACHE_TTL` 可调），列表数据最多滞后 TTL 秒（列表非强一致数据）；
- 缓存为**进程内**：单进程部署有效；若改多进程，每进程一份缓存，可升级 Redis 共享缓存；
- 压测中 JMeter 反复请求同一热页，命中率 > 99%，因此收益显著；
  生产环境命中率取决于访问分布（首页/热门商品高、冷门筛选低），报告已注明。

### 5.5 实测效果

| 指标 | 基线（原代码） | 优化后 | 变化 |
|---|---|---|---|
| 商品查询 p95（配对 A/B） | 94 ms | **28 ms** | **−70.2%** |
| 商品查询 p50 | 69 ms | **15 ms** | −78.3% |
| 吞吐 | 103.5 req/s | **148.0 req/s** | **+43.0%** |
| 每请求 SELECT（`Com_select` 增量 ÷ 请求数） | 2.98 | **0.025** | **−99.2%** |
| 错误率 | 0% | 0% | 不变 |

## 六、优化 5：连接池参数调优

### 6.1 修改前（`app/utils/db.py`）

```python
engine = create_engine(database_url,
                       pool_size=10,
                       max_overflow=20,
                       pool_recycle=1800,
                       pool_timeout=30,
                       pool_pre_ping=True)
```

### 6.2 修改后

```python
engine = create_engine(database_url,
                       pool_size=20,       # ≥ 最大并发线程数(20)，避免取连接排队
                       max_overflow=20,
                       pool_recycle=1800,
                       pool_timeout=30,
                       # 默认关闭每次取连接前的 SELECT 1 探测（本地 MySQL、
                       # pool_recycle < wait_timeout，断连风险低）；
                       # 不稳定的网络环境可设 DB_POOL_PRE_PING=1 恢复
                       pool_pre_ping=os.getenv('DB_POOL_PRE_PING', '0') == '1')
```

### 6.3 说明

- 20 并发线程下原 `pool_size=10` 可能导致取连接等待；调到 20 与并发匹配；
- `pool_pre_ping=True` 会在每次 checkout 时多一次 `SELECT 1` 往返，本地 MySQL 场景默认关闭；
- 收益与优化 3、4 合并测量（单独拆分的边际收益较小，避免过度归因）。

## 七、优化 6：分页 COUNT 查询优化

### 7.1 修改前（`db.get_all_products_paginated`）

```python
query = session.query(Product).options(joinedload(Product.seller))
if status: query = query.filter(Product.status == status)
...
total = query.count()          # 对带 joinedload 的 ORM 查询做子查询计数
items = query.order_by(Product.created_at.desc()).offset(...).limit(...).all()
```

### 7.2 修改后

```python
filters = []
if status: filters.append(Product.status == status)
if seller_id is not None: filters.append(Product.seller_id == seller_id)
if name_keyword: filters.append(Product.name.like(f'%{name_keyword}%'))

total = session.query(func.count(Product.id)).filter(*filters).scalar() or 0
items = (session.query(Product)
         .options(joinedload(Product.seller))   # 保留 joinedload，避免卖家信息 N+1
         .filter(*filters)
         .order_by(Product.created_at.desc())
         .offset((page - 1) * per_page).limit(per_page).all())
```

### 7.3 说明

- COUNT 与分页查询复用同一组过滤条件；
- COUNT 使用独立的 `COUNT(id)`，避免对带 eager-load 的查询再做子查询计数；
- 收益与优化 3、4 合并测量。

## 八、安全语义与兼容性（优化没有削弱安全能力）
