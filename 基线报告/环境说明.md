## 2. 安全配置及接口口径

- 地址为 `http://127.0.0.1:5001`，**TLS未启用**。这是一套明确记录的当前版本HTTP基线。
- `TUNNEL_ENABLED=1`：登录使用现有SM2数字信封+SM4-CBC；每次请求生成新的key、IV、Nonce和时间戳，响应解密后检查业务成功及令牌。
- 商品查询、加购物车、下单和订单回查按当前接口实现使用JWT，不额外改变其隧道覆盖范围。
- 当前登录限流装饰器在原代码中被注释，本次没有将其关闭作为优化；加车、下单和订单回查共享每IP每60秒100次的计数，保持启用。
- 本次不会修复CBC到GCM的协议差异或新增HTTPS。未来改变安全协议、服务模式或限流配置后，需要重新建基线；当前成绩不能证明GCM或HTTPS下的性能。

## 3. 数据集及快照重置

使用独立测试库，**不会清空现有业务库**。`database_fixture.py` 仅允许重置代码中固定的 `perf9_baseline`，不接受任意库名作为重置目标。

初始14张表，非空表为20个普通用户、1个商户、100个商品和20个独立购物车；订单、订单明细、购物车明细、刷新令牌和审计事件初始均为空。测试账号和商品使用perf9前缀。每线程固定一个账号和商品，避免多个线程共用购物车。

初始快照SHA256：`2ac71f208feacab8dd6fca225f1818698ad46d6879e710a76bb647640c59b100`。这是本机数据状态的指纹，完整快照含密码哈希，仅保存在被忽略的 `performance/.local/baseline-snapshot.json`。新机器重新生成的随机密码、哈希和日期可能不同，因此其指纹应重新记录，不要求与本机一致。

每轮：恢复快照并校验 → 运行预热 → 再恢复相同快照并校验 → 正式采样 → 保存采样后数量和指纹。恢复包含14张表内容及自增序列，不只是清理购物车。后端进程保持运行，保留预热后的进程状态，正式测量重新获取登录态。

每轮开始的 `before-warmup.json`、`before-measurement.json` 必须匹配初始指纹。下单测量后还核验订单/明细数量恰好增加40条、购物车明细回到0，作为业务确实执行的独立证据。

## 4. 固定负载与采样方法

| 参数 | 登录 | 商品查询 | 下单 |
| --- | --- | --- | --- |
| 线程数 | 2 | 2 | 2 |
| 启动时间 | 1s | 1s | 1s |
| 预热 | 每线程3次，单独JMeter进程和结果目录 | 同左 | 同左 |
| 正式循环 | 每线程20次，共40个业务样本 | 同左 | 同左 |
| 轮数 | 3 | 3 | 3 |
| 请求间隔 | 每个循环HTTP请求前固定1500ms | 同左 | 同左，包含准备加车和订单回查 |
| HTTP连接 | keep-alive，连接超时5s，响应超时30s | 同左 | 同左 |

选择2线程和1500ms是为了在当前共享100次/分钟限流下建立同口径的低负载基线；下单每轮含加车、下单、回查，三类请求都会占用限流预算。没有以关闭限流或忽略429换取错误率。这不是20线程高负载或容量上限测试。

正式业务采样器分别为 `business-login`、`business-products`、`business-order`。准备登录、数据分配、加购物车和订单回查均保留在原始JTL中，但HTML业务统计通过 `^business-.*` 过滤，不混入p95和吞吐量。准备或回查失败会使整个运行失败，而非被过滤掩盖。

HTTP elapsed包含后端解密、业务和响应加密的耗时；不含JMeter客户端预处理加密、断言解密及定时等待。吞吐量为该业务采样器的样本数除以其首个请求开始至最后请求结束的时间，受到上述等待和业务流程影响，不是去掉等待后估算的理论QPS。p95直接使用归档JMeter HTML统计中的 `pct2ResTime`，避免不同算法混用。

## 5. 监控及证据文件

用psutil 7.2.2每秒采集本机整机CPU/内存、后端进程、实际连接的MySQL进程、JMeter Java进程CPU和RSS。PID由启动记录及MySQL pid_file获取。

- `*_cpu_pct_one_core`：一个逻辑核满载计100%，多线程进程可超过100%。
- `*_cpu_pct_host`：上述值除以32逻辑核，表示相对于整机CPU容量的百分比。
- `*_rss_mib`：进程驻留内存字节数除以1048576；不是系统提交内存。
- `system_cpu_pct`、`system_memory_pct`：整机百分比；`system_used_mib`为系统已用物理内存。

监控CSV保留JMeter整个启动、请求和报告生成过程。`summary.json` 的资源汇总仅取正式业务首个HTTP请求开始至最后一个结束的时间窗；预热监控另存，不计入正式指标。每轮指标应与其监控文件一起解读。指标定义依据[psutil官方API](https://psutil.io/api/)。

`基线报告/baseline/<批次>/` 目录包含环境JSON、源码清单、工作区差异、9轮原始JTL、HTML报告、监控CSV、每轮前后状态、指标CSV和完成标记。完整私密快照及账号CSV不会复制到交付目录。

## 6. 从新机器复现

在 `-3` 仓库根目录执行。先准备Windows、MySQL 9.2和Python 3.13，并把源码放到本机工作目录。

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r ./performance/requirements-baseline.txt
.\.venv\Scripts\python.exe ./performance/setup_tools.py
```

复制 `后端flask/.env.example` 为 `.env`，填入本机数据库权限和OpenSSL路径。数据库账号需能创建和操作独立测试库。JWT/SECRET/SM4字段必须用新随机值；两个SM2公私钥对要匹配，不要把本机现有密钥公开。可以在本机Python交互环境用如下逻辑生成十六进制密钥对，再填入模板：

```python
import secrets
from gmssl import sm2
def pair():
    sk = f"{secrets.randbelow(int(sm2.default_ecc_table['n'], 16) - 1) + 1:064x}"
    pk = sm2.CryptSM2(private_key=sk, public_key='')._kg(int(sk, 16), sm2.default_ecc_table['g'])
    return sk, pk
# 在本机保存pair()生成的两对密钥，分别对应FLASK与VUE；勿发布私钥。
```

首次初始化（不要在已有基线批次运行中操作）：

```powershell
.\.venv\Scripts\python.exe ./performance/database_fixture.py init
.\.venv\Scripts\python.exe ./performance/seed_data.py --database perf9_baseline --users 20 --products 100
.\.venv\Scripts\python.exe ./performance/database_fixture.py snapshot
powershell -NoProfile -ExecutionPolicy Bypass -File ./performance/start-backend.ps1 -Port 5001 -Database perf9_baseline -Python ./.venv/Scripts/python.exe
.\.venv\Scripts\python.exe ./performance/run_baseline.py
```

本机环境已经初始化并启动，重新采集整批只需运行最后一条命令；驱动会按快照恢复。`snapshot`拒绝覆盖已有快照，避免悄悄更换比较起点。默认生成新批次目录，不覆盖旧证据。若只单独调试接口，必须指定独立端口：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File ./performance/run-jmeter.ps1 -Scenario order -Port 5001 -Threads 2 -Loops 2 -ThinkMs 1500
```

`.local/users.csv`和`.local/fixtures.json`对应最近一次seed的目标库；不要拿这份CSV访问另一数据库。该基线流程明确固定为perf9_baseline及5001端口。
