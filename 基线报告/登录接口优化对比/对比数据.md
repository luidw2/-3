> 保守写报告可用 -13.7%；若按干净复测口径可用 -18.9%。两种口径都远小于 20%，登录仍建议采用"已达标保持证明"。

## 4. 优化内容

1. **登录链路数据库写合并**：原实现成功登录触发 3 次独立会话/3 次提交
   （`reset_failed_login` + `create_refresh_token` + `log_security_event`），
   改为：仅在确有失败计数/锁定标记时用一个短事务重置，随后一次事务写入
   `refresh_token` 与登录成功审计（无行锁）。
2. **日志降噪**：控制台默认只输出 WARNING、关闭 werkzeug 逐请求访问日志，
   保留 `backend.log` 中的 `REQ ... (xxms)` 证据日志。

## 5. 失败尝试记录（重要，报告里不要作为优化结果）

第一版实现把"行锁重置 + 两条 INSERT"放在**同一个长事务**里：
单账号 20 并发时所有请求争抢同一 user 行锁，且持锁时间从约 2.5ms 拉长到约 6.5ms，
结果 p95 反而升到 **1281ms**（`Test_user_login_after1.jtl`，GUI 模式采集）。
修正为"短事务重置 + 无行锁写审计/令牌"后恢复正常并优于基线。

## 6. 结论

- 在不降低 bcrypt cost（保持 12）的前提下，p95 下降约 14%~19%，吞吐 +15%~16%，错误率 0%；
- 两版本 CPU 峰值均约 90%（基线 88.5%~90.9%，优化版 90.9%~91.3%），CPU 已接近饱和，
  说明登录性能上限由 bcrypt 计算决定；
- 登录接口优化后 p95 约 370~440ms，稳定低于 1s 业务阈值，可写"已达标保持证明"。
