# 登录接口性能优化说明（第 8–9 周）

> 项目：安全电子商务系统（Flask + Vue + SM2 隧道）
> 被测接口：`POST /user/login`
> 优化日期：2026-10-29
> 关联数据：`基线报告/登录接口优化对比/`（A/B 原始 JTL、PerfMon、JMeter 计划、`对比数据.md`）
> 关联脚本：`后端flask/docs/第8-9周性能基线/scripts/quick_breakdown.py`

---

## 1. 背景与目标

任务书第 4 条要求：“使用 JMeter 对登录、商品查询和下单接口建立基线……以同一环境复测，优化后 p95 较基线下降不少于 20% **或给出已达标的保持证明**，错误率不高于 1%”。

本说明记录**登录接口**的优化过程：

- 优化前：成功登录一次需要 **4 次数据库会话、3 次独立提交**，且每请求写 2~3 条同步日志（控制台 + 文件）；
- 优化后：成功登录压缩为 **2 次数据库会话 / 2 次提交**（正常登录不持有 user 行锁），并降低日志同步 I/O；
- 兼容性：不改变密码校验算法（bcrypt cost=12 保持不变）、不改变令牌/审计语义、不影响证书登录。

## 2. 瓶颈定位（先有数据再改代码）

### 2.1 组件级实测（脚本 `quick_breakdown.py`）

单请求纯服务时间 **218.7 ms**，分解如下：

| 组件 | 耗时 | 占比 |
|---|---|---|
| **bcrypt 口令校验（cost=12）** | **201.4 ms** | **92.1%** |
| DB 查用户 | 4.1 ms | 1.9% |
| DB 重置失败计数 | 2.5 ms | 1.1% |
| DB 写 refresh_token | 6.3 ms | 2.9% |
| DB 写登录审计 | 3.2 ms | 1.5% |
| 其它（Flask/JSON/日志等） | ≈1.2 ms | <1% |

结论：登录是 **CPU 密集型**接口，bcrypt 占 92%；数据库相关写操作合计约 **12 ms**，是本次安全优化能动的部分（理论收益上限约 5%）。

### 2.2 负载基线（优化前）

- 20 线程 / Ramp-Up 1 / Loop 100，每轮 2000 样本，错误率 0%；
- JMeter 非 GUI 模式基线：**p50 = 411 ms，p95 = 505 ms，吞吐 46.72 req/s**（三轮中位数）；
- CPU 峰值约 88.5%~90.9%，已接近饱和 → 也说明无法靠工程优化拿到 20% 的降幅。

> 注：更早用 JMeter **GUI** 模式采集的基线 p95 为 778 ms；GUI 客户端开销会明显抬高 p95，
> 因此正式基线/对比统一改用**非 GUI（CLI）模式**，本文所有数据均为 CLI 模式。

**一次成功登录 = 4 次数据库会话 + 3 次调用：**

| 步骤 | 函数 | 数据库操作 | 行锁 | commit |
|---|---|---|---|---|
| 1 | 视图前面已执行 `db.get_user_by_username` | SELECT | 无 | — |
| 2 | `db.reset_failed_login(user_)` | SELECT … FOR UPDATE + UPDATE | **有** | 1 |
| 3 | `auth.generate_refresh_token(user_)` → `db.create_refresh_token` | INSERT | 无 | 1 |
| 4 | `db.log_security_event(...)` | INSERT | 无 | 1 |

### 3.3 原版 `db.py` 三个函数（优化前）

```python
def reset_failed_login(user):
    with Session() as session:
        try:
            if hasattr(user, 'role') and user.role == 'seller':
                db_user = session.query(Seller).filter_by(id=user.id).with_for_update().one()
            else:
                db_user = session.query(User).filter_by(id=user.id).with_for_update().one()
            db_user.failed_attempts = 0
            db_user.lock_until = None
            session.commit()
        except Exception as e:
            session.rollback()
            print(f"重置失败登录计数错误: {e}")


def create_refresh_token(user_id=None, seller_id=None, token=None, expires_at=None):
    with Session() as session:
        try:
            rt = RefreshToken(user_id=user_id, seller_id=seller_id,
                              token=token, expires_at=expires_at)
            session.add(rt)
            session.commit()
        except Exception as e:
            session.rollback()
            print(f"创建刷新令牌失败: {e}")
            raise


def log_security_event(event_type: str, username: str, details: str):
    with Session() as session:
        try:
            event = SecurityEvent(event_type=event_type, username=username, details=details)
            session.add(event)
            session.commit()
        except Exception as e:
            session.rollback()
            print(f"记录安全事件失败: {e}")
```

**问题：**

1. 每次成功登录固定 3 次 commit（MySQL `innodb_flush_log_at_trx_commit=1`，每次 commit 都刷盘），且每次都要从连接池取/还连接；
2. `reset_failed_login` 即使 `failed_attempts=0`、`lock_until=NULL` 也照样 `SELECT … FOR UPDATE` + UPDATE，白加行锁、白写一次；
3. 同一账号并发登录（压测就是 20 个 VU 同一账号）时，这个行锁会被反复争抢。

### 4.1 新版 `login.py` 成功分支（优化后）

### 4.2 新增 `db.complete_login_success()`（`db.py` L1356–L1404）

```python
def complete_login_success(user, refresh_token, expires_at, event_details, need_reset=False):
    is_seller = getattr(user, 'role', '') == 'seller'
    model = Seller if is_seller else User
    # ---------- 第一步（仅必要时）：短事务重置失败计数，行锁持有时间最短 ----------
    if need_reset:
        with Session() as session:
            try:
                db_user = session.query(model).filter_by(id=user.id).with_for_update().one()
                db_user.failed_attempts = 0
                db_user.lock_until = None
                session.commit()
            except Exception as e:
                session.rollback()
                print(f"重置登录失败计数失败: {e}")
                raise
    # ---------- 第二步：写 refresh_token + 审计（无行锁，单事务提交） ----------
    with Session() as session:
        try:
            session.add(RefreshToken(
                user_id=None if is_seller else user.id,
                seller_id=user.id if is_seller else None,
                token=refresh_token,
                expires_at=expires_at,
            ))
            session.add(SecurityEvent(
                event_type='USER_LOGIN_OK',
                username=user.username,
                details=event_details,
            ))
            session.commit()
            return True
        except Exception as e:
            session.rollback()
            print(f"合并写入登录成功记录失败: {e}")
            raise
```

**与优化前的对比：**

| 项目 | 优化前 | 优化后 |
|---|---|---|
| 会话数（成功登录） | 4 | **2**（正常路径：1 次查用户 + 1 次写令牌与审计） |
| commit 次数 | 3 | **1**（正常路径） |
| user 行锁 | 每次登录都加 | **只有失败计数/锁定标记非空时才加** |
| 审计事件 | 独立事务 | 与 refresh_token 同事务（不丢） |
| refresh_token | 生成即入库 | 生成后与审计一起入库（仍同步落库） |

### 4.3 新增 `auth.generate_refresh_token_value()`（`auth.py` L123–L131）

```python
def generate_refresh_token_value(user_or_seller):
    now = _now_utc()
    exp = now + timedelta(days=REFRESH_TOKEN_TTL_DAYS)
    token = secrets.token_urlsafe(48)
```

新函数只负责“生成随机串 + 过期时间”，落库交给登录链路的合并函数。

## 5. 安全语义保持说明

| 关注点 | 优化后行为 |
|---|---|
| bcrypt 强度 | 未改动：仍为 cost=12（`gensalt()` 默认值） |
| refresh_token | 仍同步落库（客户端拿到令牌时库里一定有记录） |
| 登录成功审计 | 与 refresh_token 同一事务提交，不会丢失 |
| 失败计数/锁定 | 逻辑不变；仅当确有失败记录/锁定标记才执行重置（成功登录后仍会清零） |

| 证书登录 | 未受影响（原 `generate_refresh_token` 保留） |

## 8. 失败尝试记录（重要教训）

**第一版实现**把“行锁重置 + 两条 INSERT”放进同一个长事务：

```python
# 第一版（有缺陷，已回滚修改）
with Session() as session:
    db_user = session.query(User).filter_by(id=user.id).with_for_update().one()  # 持锁
    if db_user.failed_attempts or db_user.lock_until is not None: ...
    session.add(RefreshToken(...))     # 持锁期间 INSERT
    session.add(SecurityEvent(...))    # 持锁期间 INSERT
    session.commit()                   # 锁一直持有到提交
```

**现象**：p95 从 778 ms 升到 **1281 ms**，吞吐从 45.4/s 掉到 **32.5/s**，但 CPU 峰值几乎不变（78% vs 77%），
说明请求在**等锁**而不是在计算。

**原因**：压测是 20 个 VU 都用同一个账号 `user_1`，20 个请求争抢同一行 user 记录；
第一版把行锁持有时间从约 2.5 ms 拉长到约 6.5 ms，排队被放大。

**修正**：把重置失败计数改成“仅必要时才进入短事务加锁”，正常登录不碰 user 行锁（即第 4.2 节的最终实现）。
修正后恢复正常并优于基线。

> 教训：性能优化必须结合**测试数据分布**（这里是无 CSV 账号池、单账号 20 并发）来验证；
> 不能只看单线程耗时。

## 10. 结论与后续

1. **结论**：在不降低 bcrypt 强度（cost=12）的前提下，登录接口 p95 由 **505 ms 降至 436 ms（−13.7%）**，
   干净复测口径 **−18.9%**，吞吐 **+14.8%~15.8%**，错误率保持 **0%**；
   登录 p95 稳定低于 1 s 业务阈值，可作为任务书允许的「**已达标保持证明**」。
2. **20% 指标的安排**：登录受 bcrypt 安全成本限制无法安全达到 20%，
   该项指标交由**商品查询接口**承担（其 CPU 仅约 34%，优化空间大）。
3. **后续优化计划**：
   - 商品查询：先用 CLI 模式重测基线 → JWT 鉴权缓存 → 连接池参数 → 热点商品缓存（每项单独复测）；
   - 下单接口：补基线（任务书要求三个接口），再针对 `create_order` 的 N+1 查询与索引做优化；
   - 全流程统一使用非 GUI 模式与“单实例检查”，保证口径一致。
